# shimborska.dgroza.ru

Постоянные правила работы с репозиторием сайта Виславы Шимборской.

## Документация

- `README.md` — запуск, команды и карта документации.
- `docs/CONTENT.md` — каталог, шаблоны и правила изменения произведений.
- `docs/OCR.md` — пошаговое распознавание произведений по снимкам и локальный
  журнал прогресса.
- `docs/FRONTEND.md` — Blade, CSS, JavaScript, accessibility и ручные проверки.
- `docs/SEO-DESCRIPTIONS-PILOT-2026-08-03.md` — журнал текущего SEO-пилота,
  его условия, события и контрольные срезы.
- `sources/README.md` — структура локального архива и правила карты источников;
  `sources/POEMS.md` — текущие соответствия произведений и источников.
- `DEPLOYMENT.md` — переносимые production-требования приложения.

Перед изменением соответствующей области прочитать её документ. Подробности не
дублировать в этом файле.

## Границы проекта

- Runtime и зависимости задаются `composer.json` и `composer.lock`; базы данных
  и frontend-сборки нет.
- Сайт контентный и read-only. Не добавлять пользовательское или постоянное
  состояние, миграции либо команды, изменяющие пользовательские данные.
- Сохранять публичные URL, имена маршрутов, тексты, кодировку и визуальный стиль,
  если пользователь прямо не попросил обратного.
- Frontend остаётся на Blade, CSS и vanilla JS. Не добавлять npm, Vite, jQuery,
  UI-фреймворки или новые архитектурные слои без явной необходимости.
- Не помещать в Git секреты, production `.env`, ключи или сертификаты.

## Области изменений

- Каталог, маршруты произведений, тексты и связанную разметку изменять по
  `docs/CONTENT.md`.
- OCR-задачи и локальный журнал вести по `docs/OCR.md`; архив и карту источников
  — по `sources/README.md`.
- Изменения Blade-layout, CSS и JavaScript проверять по `docs/FRONTEND.md`.
- Перед работой над SEO-экспериментом читать его датированный документ и
  записывать туда связанные релизы, события, контрольные срезы и решения.
  Новые журналы называть по схеме `docs/SEO-<EXPERIMENT>-YYYY-MM-DD.md`.
- Production-требования приложения хранить в `DEPLOYMENT.md`; реализация этих
  требований в конкретной инфраструктуре находится вне этого репозитория.

## Проверки и зависимости

- Команды запуска и автоматических проверок брать из `README.md`.
- Проверки выбирать пропорционально фактическому риску изменения: после
  небольшой локальной правки выполнять только целевые автоматические и ручные
  проверки того поведения, которое изменилось или могло сломаться.
- Не повторять полный дорогой набор после каждой правки в серии: промежуточные
  изменения проверять минимально, а согласованный набор — один раз на
  контрольной точке.
- Для подтверждённой по источнику точечной правки текста существующего
  произведения применять ускоренный режим из `docs/OCR.md`. Перед отдельным
  коммитом достаточно его целевых проверок; полный `composer check` выполнять
  на контрольной точке не более чем после пяти произведений.
- Полный `composer check` и всю применимую ручную матрицу из
  `docs/FRONTEND.md` проходить перед релизом, по прямому запросу пользователя,
  на контрольной точке, а также после глобальных изменений общих стилей,
  layout, breakpoints, JavaScript-контрактов или печати.
- `composer sitemap` выполнять только при изменении каталога, публичных путей,
  sitemap-кода или конфигурации либо по прямому запросу; текст существующего
  произведения на sitemap не влияет.
- Если изменение делает неточным профильный документ, обновлять его в рамках
  той же задачи.
- Задача завершена только тогда, когда код, тесты и документация согласованы.
- При изменении зависимостей согласованно обновлять `composer.json` и
  `composer.lock`; lock-файл вручную не редактировать.
- Сохранять чужие незакоммиченные изменения и проверять diff перед коммитом.

## Deployment и Git

- Условия обновления deployment-контракта определены в `DEPLOYMENT.md`.
- Обычный релиз контента или исправление кода не требует изменения deployment-
  контракта, если требования приложения не поменялись.
- Не добавлять в `DEPLOYMENT.md` инфраструктурные детали конкретного сервера.
- Не выполнять push, merge или production-деплой без явного запроса.
- Не применять destructive Git-команды и не запускать миграции.
